## Review rationale

The existing plain controller remains unchanged and owns synchronous disposal before replacement. The injected `View.Surface` accepts the plain engine. The proposed adapter-local bitmap presentation can use mygo's public API without putting native types into the controller/UI boundary. Pinned mygo `ui/bitmap.go:150-176` documents main-thread Update and retained RGBA pixels; implementation must retain a displayed buffer until replacement rather than recycle it while the bitmap uses it. The bounded mailbox allows an ownership-safe implementation, but the eventual candidate must demonstrate it.

Pinned `render.h:32-145` permits software rendering into memory, requires serialized render calls, prohibits reentrant callback rendering and render-to-control wait dependencies, and requires context release before core destruction. Spec lines 70-100 impose separate render/control owners, signaling-only callbacks and ordered teardown consistently with those constraints. Four-byte software formats include an unused byte, not guaranteed alpha (`render.h:363-408`); implementation must produce correct opaque pixels and alignment for the public bitmap. No render implementation or performance result exists yet.

Pinned `client.h:99-129, 506-542` confirms async completion/order must be observed and destruction can block. Spec lines 62-67 and 94-117 retain reply ordering, complete synchronous Close, one core and the original external 100ms cancel bound. It explicitly rejects a stalled gate, early closed snapshot, overlapping cores and hidden background shutdown. That is a valid experiment with a potentially negative answer, not a contradiction promising bounded destruction. Queue pressure must not prevent the out-of-band shutdown path; callback/render quiescence and partial initialization need exact-candidate review. Pinned purego `func.go:43-110` leaves ABI layout and retained-memory correctness to the caller. Its `syscall_unix.go:22-56` retains callback registrations for process lifetime; use bounded reusable trampolines without retained per-session objects, or otherwise demonstrate bounded ownership. The plan leaves this strategy to reviewed implementation and makes ABI failure a stop condition.

Pinned options sections at lines 2366, 5774 and 5825 establish audio-files, custom-header list and referrer APIs; client API 2.6 is declared at `client.h:251`. They do not prove both-stream propagation or fatal external-audio behavior. AC-04/05 explicitly require server evidence, comma-safe lists, isolation, external track observations and failure on missing audio. Audible output/sync cannot pass from fetching or selected-track flags. No unsupported API alias is required by the plan.

The tasks are serial with ordered overlapping write scopes. RPL-001 can write its rejection report without starting RPL-002/003; successful continuation requires exact gate-one independent review. Historical smoke/contract/fixtures remain read-only, and new commands have separate stages/defaults and retained external timing/oracle bounds. AC-07 allows an honest reject/needs-human result while preserving unavailable acceptance cells. Runtime supply and later Windows/audio/target evidence are explicit execution prerequisites or later gates, not silently waived architecture requirements. Copyright/build source also supports requiring the actual build/dependency inventory rather than inferring a binary license from a flag.
